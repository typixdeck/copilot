# 真实写入后端（0.2.0）

面向 Raspberry Pi OS Trixie ARM64。GTK3 进程使用普通用户权限，点击“写入”后自动检查缓存；缺少文件时从本仓库统一固件目录下载固定哈希镜像（来源仍指向上游固定提交），通过大小、SHA-256 和镜像结构检查后，经一次 Polkit 管理员授权进入维护事务。

所有通过发布公钥验签的目录条目均可发起写入，包括当前四个官方版本与 DIY 0.3.0 / 0.2.0。`hardware_verified` 仅说明硬件验收状态，不禁用写入。未经签名的 JSON 或任意本地 bin 不能获得提权写入授权。

## 设备与授权

`/etc/typix-copilot/board.json` 是管理员维护的板载连接配置。随包配置对应 0720 板，控制器 `fe9c0000.xhci`、内部 Hub `1a40:0201`、端口 `1-1.2`。每次运行都检查 sysfs 枚举关系、产品模式、唯一直属 CDC 端口及打开后设备号；不同 CM 或 USB 拓扑必须重新验证配置，不能仅改型号名称或使用第一个 ttyACM。

固定 helper `/usr/libexec/typix-copilot-write` 只接收所选固件 ID，以及 stdin 中有界的签名目录封装与随后的镜像内容。封装固定为 8 字节 magic、4 字节大端 JSON 长度、64 字节 Ed25519 签名和原始 JSON（最大 256 KiB）；root 在接触板载设备前用安装目录中的公钥重新验签，绑定所选 ID、版本、大小和 SHA-256。它不接收文件路径、脚本、串口、地址或 esptool 参数；以隔离 Python 启动，使用 root 安装的公钥、板配置和固定 esptool 5.3.1。授权不在 GUI 中保存，也不设置免密常驻 root 服务。

## 真实事务

1. 全局锁、存储空间、固件大小/哈希/结构检查；未知目标或繁忙端口拒绝操作。
2. 已绑定正常固件的 CDC 连接仅发送 `AW_DUMP`，提取 CONFIG_P0 的电源/复位输入状态；其余原始串口数据丢弃。此状态不是物理供电连续性的保证。
3. 发送固定官方维护命令，等待相同板载端口进入 ROM；运行态 CDC 需要 DTR 连接标志，ROM 不使用通用 DTR/RTS 复位。
4. 在 ROM 中验证 chip ID 9、安全启动/加密/下载配置与 Flash 容量；受保护或无法验证的状态停止。
5. 读取整个 8/16 MiB Flash，校验传输、落盘、重新读取文件核对，保存本机私有备份。备份完成前不会擦除或写入 Flash。
6. 写入偏移 `0x000000`，固定 `keep` 参数，不执行 erase-all，不自动断线重连重试。范围来自所选镜像实际长度、分区和芯片容量，额外检查镜像头声明的 Flash 容量。例如 2026-09-10 文件范围为 `[0x000000, 0x3cfe88)`，扇区擦除范围 `[0x000000, 0x3d0000)`，会覆盖 NVS 设置。
7. 重新读回整个写入范围，逐字节及 SHA-256 与输入比较；不只依赖工具的写后 MD5。
8. 清除且读回确认 FORCE_DOWNLOAD_BOOT 位，再发 ESP32 watchdog reset；等待同一端口恢复正常 USB 固件枚举。

旧官方固件没有可信运行版本握手。即使全部完成，准确结果也是“写入已校验，设备已重新连接；运行版本待确认”，不把 USB 枚举等同于版本证明。

## 本地数据与中断

- 普通用户缓存：`~/.cache/typix-copilot/artifacts/<sha256>.bin`，每次复用重新校验。相邻 `<sha256>.<元数据摘要>.proof` 按准确版本保存原始签名目录，支持从在线目录移除后的旧版本。兼容旧 `<sha256>.proof`；「本地固件」移除所选版本凭据，仅在没有其他有效版本共用该文件时删除 bin，不删除备份或记录。
- 公开给本机 GUI 的最小结果：`/var/lib/typix-copilot/status.json`；仅保留最近 20 个任务的固件 ID、版本、镜像 SHA-256/大小、阶段、布尔结果和随机任务编号，没有芯片唯一标识或原始串口内容。
- 私有备份及审计：`/var/lib/typix-copilot/private/<随机任务号>/`，目录 0700、文件 0600。Flash 备份可能包含设置，禁止上传到 GitHub 或复制进公开发布材料。
- 独立的私有维护状态记录与显示历史分离，后续失败请求不会抹掉尚未结束的 ROM 会话。允许重新明确授权、向同一板载连接写入签名目录镜像；不自动反复刷写。

下载阶段可取消；授权开始后锁住页面导航及正常退出，不向写入 helper 发送取消信号。GUI 意外消失后 helper 忽略常规挂断信号并继续已开始事务，进度管道采用有界非阻塞写入；重新打开界面读取本机结果。操作系统强杀、掉电或内核故障无法由 GUI 阻止，残留进行中状态不能自动视为成功。写入开始后的进度日志落盘失败也不打断 Flash 协议，结果标记记录保存不完整。

失败时保留缓存和已有备份，不声称自动回滚。尤其“尚未开始写入”也可能已经进入 ROM。Linux 重启不保证让 ESP32/AW 掉电或恢复；若维护 USB 仍能连接，可重新授权写入。若 USB 不再可达，可能必须拆机接触 BOOT/RESET 或使用已核对的外部维护连接；不通过猜测 GPIO/I2C/屏幕 MUX 恢复。

## 构建与验证

```sh
python3 tools/build-deb.py
PYTHONPATH=src python3 -m unittest discover -s tests -v
python3 tools/check-live-gtk.py
```

构建器下载并校验固定 esptool 5.3.1 源码归档（SHA256 `125781f36e6a2d08c484524a45f340694675368b5eeead9d0cb21b2034a91d98`），只打包 Python 包、必要 stub 与许可证；其余依赖使用 Debian 包。系统已有 esptool 不被覆盖。`.deb` 声明架构、Trixie 兼容性和依赖，`build/payload-manifest.json` 可核对安装内容。

单元/GTK 测试使用明确的替身，不触碰硬件；真机结果另行记录，不能从测试通过推断已刷写。

## 旧协议兼容与硬件验收状态

旧协议缺少 AW_DUMP 时，普通界面拒绝未验证的供电状态。写入器保留受限的首次升级许可机制供人工审查后的实验使用，GUI 与软件包不会生成此许可。许可由管理员维护，绑定板配置、目标固件、认证用户和单次启动，在五分钟内有效且只消费一次；不能因 AUDIO_DUMP 正常就宣称供电安全。维护恢复也不能自动复用已消费的许可。

2026-09-14 的 CM4 测试中，官方 2026-09-10 镜像完成实际写入并保存完整私有备份，但独立读回校验中断。随后整机重启恢复了两侧显示，不能用显示恢复代替校验成功。0.1.3 后续测试又在备份读取期间通信失败，尚未开始擦写；64 KiB 分段没有解决问题。

0.1.4 保留严格的失败状态和固定类型诊断，不把未知结果显示为成功。在线目录和下载功能仅在本机以替身及真实公开文件验证，未恢复硬件维护测试。完整刷写链路尚未验收，请暂停重复刷写；恢复操作必须基于实际设备状态另行检查。

0.2.0 移除单一官方版本白名单，统一在线和本地缓存写入。软件测试覆盖六个真实发布镜像与替身硬件事务，未在本轮重新连接串口或刷写；既有通信故障仍待单独真机验证。目录签名与包内离线副本由 `tools/sign-firmware-index.py` 同步生成。
